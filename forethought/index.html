Interfaces with forethought.

Most interface polish is about the moment after you touch something. This gallery is about the moment before. Every exhibit shows you the consequence before you commit, remembers what you did last time, or tells you plainly what it doesn't know yet.

Foresight
Preview the result while the finger is still down. Releasing commits, sliding away cancels.
Memory
Controls carry history: your last value, the default, where you already read, what you changed.
Candour
Show ranges instead of fake precision, time instead of spinners, and the true cost of an action.

Turn on X-ray, then touch anything.

You'll see each control's touch area, your finger's speed and direction, the gesture the page decided you made, and every haptic it fired, named as the Flutter call that would fire it on a phone.

Room I

Instruments

The basics: buttons, toggles, dials, sliders, fields and progress. Each keeps the shape people already know and adds one capability the old version never had. Tap works everywhere; the new part is there when you reach for it.

Room II

Expeditions

Bolder territory. Each exhibit comes from a technique that has worked somewhere specific (a research lab, a classic desktop OS, a booking form) and hasn't yet reached phone interfaces. Each one cites where it comes from.

Room III

Proposals

Six concepts of my own. None of them depends on a costume borrowed from a physical object. Each starts from a problem people hit every week (undo, going back, estimating, comparing, listening, prioritising) and solves it with a gesture you can guess on the first try.

Review

Reading the other gallery

"Touch" is a serious piece of work: four volumes, 80 exhibits, real spring physics and a "Why" line on every one. I read all four files closely, the prose and the code. This is what it gets right, where it stops short, and how this gallery answers.

What it does well

  • Physics over durations. Springs are interruptible and frame-rate independent. That is the right foundation, and this gallery keeps it.
  • Every exhibit justifies itself. The one-line "Why" is a good habit. Some are admirably honest, such as admitting that research on skeleton screens is mixed.
  • Craft in the hard ones. The page curl uses the real fold geometry. The swipe deck carries release velocity into the fling.
  • Restraint notes. "Use sparingly, once per flow" on the disintegrate effect shows taste.

Where it stops short

  • A formula in place of an insight. By Volume IV every pitch is a borrowed object: seesaw, hourglass, zipper, snow globe, tape measure, envelope, wax seal. Costumes age fast. Several also turn a one-tap action into a multi-second ritual, which is a cost on anything people do daily.
  • It preaches accessibility it doesn't practise. The notes say every custom control gets Semantics. The pages contain no tabindex, no role and one keyboard handler across all 80 exhibits. Native buttons still focus, but the dials, sliders, decks and canvases can't be reached or operated without a finger or a mouse.
  • It fights the page. 42 touch-action:none rules capture vertical drags, so the footer has to tell you to "scroll the page by dragging on the captions". On a phone, the gallery breaks the most common gesture there is.
  • Recipes are sketches. The Flutter recipes average 4.8 lines, for example "ScaleGestureDetector: scale 1.35 on a tile → level++". You can't estimate or build from that.
  • It repeats itself. Seven exhibits are "hold to do X". Three hide content behind a physical cover (fold, zip, scratch). Two set a value by circular drag. "Nothing repeated" holds for names, not for mechanics.
  • It ignores the viewer. No volume reads prefers-color-scheme. Only one volume styles keyboard focus at all, and the claim of "feedback in one frame" can't be checked anywhere on the page.

How this gallery answers

  • Borrowed objects as the ideaPrinciples as the idea: foresight, memory, candour. Each exhibit keeps the control people already know and adds one capability.
  • Rituals that slow frequent actionsTap still works everywhere. The new behaviour waits for the finger that reaches further: a longer drag, a held press, a faster flick.
  • Accessibility in the notes onlyAccessibility in the code. Every exhibit has keyboard operation, roles, values and live announcements, and each lists exactly how it works.
  • Captured scrollControls claim only the axis they use. The page always scrolls.
  • Claims you can't checkX-ray draws the touch area, velocity vector, recognised gesture, the exhibit's decision and every haptic, named as its Flutter call.
  • Recipes as hintsReal widget code with the actual APIs (SpringSimulation, ScrollPhysics, Semantics, CustomPainter), plus an APK blueprint below.

Blueprint

From this page to an APK

The HTML is the sketchbook. The goal is a Flutter app, so every exhibit was built on primitives that map one-to-one onto the Flutter SDK. These are the shared foundations, the parts that make 21 exhibits feel like one product.

One motion system

Every animated value is a spring with velocity, so any motion can be grabbed mid-flight and thrown somewhere else. Four tokens cover the whole gallery, the same four the page uses.

abstract final class FtSpring {
  static const snappy = SpringDescription(mass: 1, stiffness: 600, damping: 44);
  static const smooth = SpringDescription(mass: 1, stiffness: 260, damping: 30);
  static const bouncy = SpringDescription(mass: 1, stiffness: 320, damping: 16);
  static const gentle = SpringDescription(mass: 1, stiffness: 120, damping: 20);
}

class SpringValue extends ChangeNotifier implements ValueListenable<double> {
  SpringValue(TickerProvider vsync, double v, {this.spring = FtSpring.smooth})
      : _c = AnimationController.unbounded(vsync: vsync, value: v) {
    _c.addListener(notifyListeners);
  }
  final AnimationController _c;
  SpringDescription spring;
  static bool reduceMotion = false; // set from MediaQuery.disableAnimationsOf

  @override double get value => _c.value;
  void jump(double v) => _c.value = v;
  void animateTo(double target, {double? velocity}) => reduceMotion
      ? _c.value = target
      : _c.animateWith(SpringSimulation(spring, _c.value, target, velocity ?? _c.velocity));
  @override void dispose() { _c.dispose(); super.dispose(); }
}

X-ray, shipped as a debug overlay

The same inspector lives at the root of the app in debug and profile builds. A translucent Listener sees every pointer without joining the gesture arena, so it never changes what the exhibits receive.

class XRay extends StatefulWidget {
  const XRay({super.key, required this.child});
  final Widget child;
  @override State<XRay> createState() => _XRayState();
}

class _XRayState extends State<XRay> {
  final _trackers = <int, VelocityTracker>{};
  final _touches = ValueNotifier(<int, Offset>{});

  void _track(PointerEvent e) {
    _trackers[e.pointer]?.addPosition(e.timeStamp, e.position);
    _touches.value = {..._touches.value, e.pointer: e.position};
  }

  @override
  Widget build(BuildContext context) => Listener(
    behavior: HitTestBehavior.translucent,
    onPointerDown: (e) {
      _trackers[e.pointer] = VelocityTracker.withKind(e.kind);
      _track(e);
    },
    onPointerMove: _track,
    onPointerUp: (e) => XRayLog.release(_trackers.remove(e.pointer)!.getVelocity()),
    child: Stack(children: [
      widget.child,
      IgnorePointer(child: CustomPaint(painter: XRayPainter(_touches), size: Size.infinite)),
    ]),
  );
}

A haptic vocabulary

Five words, used the same way everywhere: select for detents and snaps, light for a press, medium for a commit, heavy only for something irreversible, success for a completed flow. X-ray logs each one, so a designer can review haptics on a laptop.

enum Haptic { select, light, medium, heavy, success }

extension Fire on Haptic {
  Future<void> call() async {
    XRayLog.haptic(this);
    switch (this) {
      case Haptic.select: return HapticFeedback.selectionClick();
      case Haptic.light:  return HapticFeedback.lightImpact();
      case Haptic.medium: return HapticFeedback.mediumImpact();
      case Haptic.heavy:  return HapticFeedback.heavyImpact();
      case Haptic.success:
        await HapticFeedback.lightImpact();
        await Future.delayed(const Duration(milliseconds: 70));
        return HapticFeedback.mediumImpact();
    }
  }
}

Accessibility as a contract

  • Every custom control declares Semantics with a value and onIncrease/onDecrease, so TalkBack's volume-key adjustment works on the spiral dial, the EQ and the allocator.
  • Gesture-only shortcuts get a twin in customSemanticsActions. Deep back exposes "Back to Inbox" and "Back to Home"; drawn commands expose Complete, Star and Delete.
  • Shortcuts + Actions mirror the keyboard map on this page for Chromebooks, tablets with keyboards and DeX.
  • MediaQuery.disableAnimationsOf sets SpringValue.reduceMotion: springs jump to their target and sheens become static.
  • Every hit area is at least 48 dp, verified by meetsGuideline(androidTapTargetGuideline) in widget tests.

Performance budget

  • Target 8.3 ms per frame (120 Hz) on a mid-range phone, checked with integration_test and traceAction timelines in CI.
  • Each exhibit sits in a RepaintBoundary. Painters take repaint: listenables, so motion repaints without rebuilding widgets.
  • The wet-ink sheen, the morphing chart and the tide are FragmentProgram shaders on Impeller. Each has a plain-canvas fallback.
  • Off-screen exhibits are wrapped in TickerMode(enabled: false), so springs and loops sleep, just as they do here.

Platform details that matter

  • Deep back is bound to the back chevron, never to the screen edge, so it coexists with Android's predictive back (PredictiveBackPageTransitionsBuilder, PopScope).
  • Word-level scrubbing (III.5) uses on-device speech recognition timestamps for real voice notes, and flutter_tts progress callbacks for the demo voice. That is the only third-party dependency.
  • Everything else, including the $1 glyph recogniser and the sketch matcher, is plain Dart: no ML runtime, no network.
